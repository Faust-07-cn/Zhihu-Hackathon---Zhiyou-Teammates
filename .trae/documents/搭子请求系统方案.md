# 搭子请求系统（搭子广场）实现方案

## Context（为什么做）

当前平台的搭子关系只能由系统匹配推荐产生，用户无法**自主发起**"求搭子"请求，也无法**响应他人**的请求。本需求参考闲鱼模式补齐这条链路：

- **发布**：用户可自主创建"求搭子"请求（标题/类型/目的/标签/描述）
- **响应**：其他用户浏览请求广场，对感兴趣的请求表达"我有意向"
- **接受**：发布者在"我的请求"中从意向列表选人接受，建立搭子关系

已确认的设计决策：
- **独立"搭子广场"页面**（导航新增入口），内置"广场 / 我的请求"两个 tab
- **发布者选人接受**（闲鱼模式）：意向者提交意向 → 发布者选人 → 成组
- **广场按匹配度优先排序**：复用现有匹配打分逻辑，与自己匹配度高的请求排前面

## 后端设计（backend/app/）

### 1. 新增数据层 `app/requests.py`
内存态数据 + 操作函数（沿用 `users.py` 的内存模式，后续可换数据库）：

```python
REQUEST = {
  "id": "r01",
  "user_id": "u02",              # 发布者
  "title": "数学建模美赛找队友",
  "match_type": "interest|study|project",
  "purposes": ["竞赛组队"],       # 复用现有目的维度
  "tags": ["数学建模", "论文写作"],
  "desc": "自由描述",
  "status": "open|matched|closed",
  "intents": ["u01", "u05"],     # 已表达意向的用户 id
  "matched_user_id": None,       # 被接受的人
  "created_at": "2026-09-13 10:00",
}
```

函数：
- `list_requests()` / `get_request(id)`
- `create_request(user_id, title, match_type, purposes, tags, desc) -> req`
- `add_intent(req_id, user_id)`（发布者自己不能表达意向；重复意向幂等）
- `cancel_intent(req_id, user_id)`
- `accept_intent(req_id, owner_id, accepted_user_id)`：校验发布者身份 + 意向存在，置 `status="matched"`、`matched_user_id`
- 预置 4 条演示请求（不同用户/类型/目的，其中 1 条带 1 个意向，方便演示接受流程）

### 2. 匹配度排序（复用 `app/matching.py`）
对广场请求排序：把请求的**发布者用户**作为候选、请求的 **purposes 与 match_type** 作为打分输入：

```python
score = score_match(me, owner_user, req["match_type"], purposes=req["purposes"])["score"]
```

即"我与该发布者，按此请求的目标/类型"的匹配度。返回结果中带 `match_score` 与 `detail`（含 MBTI 互补、目的命中），前端可展示"匹配度 87%"。

### 3. 新增路由 `app/routers/requests.py`（prefix=`/api/requests`）
- `GET /?user_id=u01&match_type=&purpose=`：广场列表，按匹配度降序（未画像用户 `mbti_filter=none` 降级为纯标签排序，不阻塞）
- `POST /`：发布请求 `{user_id, title, match_type, purposes, tags, desc}`
- `POST /{req_id}/intent`：表达意向 `{user_id}`
- `DELETE /{req_id}/intent?user_id=`：取消意向
- `POST /{req_id}/accept`：发布者接受 `{user_id, accepted_user_id}`
- `GET /mine/{user_id}`：我的请求 = 我发布的 + 我表达意向的（附带意向列表与状态）

注册到 `app/main.py`。

## 前端设计（frontend/）

### 1. 新增页面 `frontend/pages/requests.html`（搭子广场）
- 顶部卡片：**发布请求**按钮 + 筛选（类型 tab：全部/兴趣/学习/项目；目的标签多选）
- **广场 tab**：请求卡片列表，卡片含发布者（头像/名字/搭子信/学校）、标题、类型+目的徽章、标签、匹配度、状态徽章（开放中/已成组）；操作按钮：
  - 非本人发布且 open → "我有意向"（点击后变"已表达意向"可取消）
  - 本人发布且 open → "查看意向 (n)"（弹模态框列出意向者，逐个"接受"）
  - matched → 展示成组对象，禁用操作
- **我的请求 tab**：分三块 —— 我发布的（含意向列表与接受按钮）、我表达意向的、已成组的

### 2. 发布表单（模态框）
字段：标题、搭子类型（单选 3 卡片，复用 `.type-card` 样式）、目的（多选胶囊，复用 `.purpose-tag`）、标签（逗号输入）、描述。提交 `POST /api/requests`，成功后刷新广场并清空表单。

### 3. 导航新增入口
所有页面（index/match/forum/me/mbti/requests）`nav-links` 增加 `搭子广场` 链接（`requests.html` 高亮 active）。窄屏布局已支持压缩，5 个链接需在 820px 断点再收紧字号验证不溢出。

### 4. `js/app.js` 新增
- `renderRequestList(reqs)`：广场卡片渲染（复用 `hashColor/firstName`）
- `renderMyRequests(data)`：我的请求三块渲染
- 发布/意向/取消/接受 四个交互函数（调用 `api()`）
- 匹配度徽章复用 `.match-score` 样式

### 5. `css/style.css` 新增
请求卡片（`.req-card`）、状态徽章（`.req-status.open/.matched`）、意向列表、模态框（`.modal-mask/.modal`）、发布表单样式。

## 验证方式

1. 后端（重启 uvicorn 后）：
   - `POST /api/requests` 创建请求 → `GET /api/requests?user_id=u01` 列表按匹配度排序且含 `match_score`
   - `POST /r01/intent`（他人）→ `GET /mine/{owner}` 意向数 +1
   - `POST /r01/accept`（发布者）→ 状态变 matched、`matched_user_id` 正确
2. 前端浏览器全流程（u01 当前身份）：
   - 发布一个"学习搭子"请求 → 广场出现且匹配度排序正确
   - 对他人请求点"我有意向" → 按钮变"已表达意向"
   - 切到"我的请求"→ 我发布的请求意向列表可见 → 接受某意向者 → 状态变"已成组"
   - 导航 5 个链接在窄屏不溢出
