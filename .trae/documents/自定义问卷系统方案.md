# 自定义问卷系统方案（搭子请求问卷筛选）

## 需求摘要

发布搭子请求时新增「是否需要问卷」选项，提高门槛；发布者需要时可自定义问卷（**仅单选题型**，每道题可标记 1+ 个「期望答案」）。意向者必须先完成问卷才能表达意向，问卷答案**同时**：
1. 展示给发布者（在「查看意向」列表中逐人可见），供其人工判断；
2. 参与匹配度计算——按「意向者答案命中发布者期望答案的比例」算出问卷匹配分，随意向展示。

## 数据模型

### 问卷对象（新数据层）
```python
{
  "id": "q01",
  "title": "搭子筛选问卷",            # 发布者起的问卷标题
  "request_id": "r05",              # 关联请求
  "questions": [
    {
      "id": "1",
      "text": "你每周可投入多少时间？",
      "options": ["5小时以下", "5-10小时", "10小时以上"],   # 2~6 个选项
      "expected": [2]                # 期望答案（选项下标列表，可为空=不计分）
    }
  ]
}
```

### 请求对象新增字段
```python
{
  ...原有字段,
  "requires_questionnaire": True,   # 是否需要问卷
  "questionnaire_id": "q01",        # 无问卷时为 None
  "answers": {                      # 意向者答案: user_id -> {question_id: 选项下标}
    "u03": {"1": 1, "2": 0}
  },
  "answer_scores": {                # 意向者问卷匹配分: user_id -> 0~100
    "u03": 66.7
  }
}
```

## 改动清单

     - `score_answers(questionnaire, answers) -> float`：命中期望答案的题数 ÷ 有期望答案的题数 × 100，无期望答案或未答时返回 50.0（中性分，与 `questionnaire_match` 一致）

   - 新增 `submit_answers(req_id, user_id, answers) -> tuple[bool, str, float | None]`：写入 answers、计算 answer_scores，返回 (成功, 提示, 分数)。

## 关键决策

- 题型仅单选（用户已确认）；每题 2~6 个选项。
- 「期望答案」由发布者在设计问卷时对每题勾选（可多勾、可不勾）；不勾的题不计入匹配分。
- 意向者必须先填完问卷才能表达意向（硬门槛，即"提高门槛"）。
- 问卷匹配分 = 命中期望答案题数 ÷ 有期望答案题数 × 100；未填/无期望答案给 50.0 中性分。
- 广场列表「匹配度」不因问卷改动（意向前无答案）。

   `python -m uvicorn app.main:app --host 0.0.0.0 --port 8001`（cwd=backend）

   - `POST /api/questionnaires` 创建问卷 → 拿 qid；

   - 带 answers 重试 → 返回 `answer_score`；`GET /mine/{uid}` 中意向人带 answers 与分数。
3. 浏览器验证前端闭环：发布→设计问卷→发布成功；另一用户「我有意向」→ 弹出填写问卷 → 提交；发布者「查看意向」→ 看到答案与匹配分；请求卡片显示「需问卷」徽标。
4. 回归：不勾「需要问卷」的普通发布流程不受影响；r01 种子问卷可正常走完整流程。

## 验收标准

- 发布时可选择是否需要问卷，选择需要后能设计并保存自定义问卷（仅单选）。
- 需问卷的请求，意向者必须填完问卷才能表达意向。
- 发布者查看意向时能看到每位意向者的答案与问卷匹配分。
- 所有改动符合既有代码风格与数据层/路由分层。
