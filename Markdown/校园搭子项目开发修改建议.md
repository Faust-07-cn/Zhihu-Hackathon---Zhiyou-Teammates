## 一、项目当前结论

目前项目已经具备校园搭子产品的基本链路：用户填写问卷、查看匹配结果、表达合作意向，发布者可以接受请求并形成小组。作为 Demo，这条链路是成立的。

但当前最大的短板是"知乎特色"还没有真正进入核心流程。现有体验更接近一个普通的校园搭子匹配网站，知乎内容、知乎用户画像和知乎 OAuth 登录尚未成为推荐结果的重要依据。黑客松展示时，评委很可能会追问：为什么一定要用知乎来做，而不是普通问卷匹配？

因此，后续修改不应只是继续堆页面，而要围绕一个问题集中强化：**用户为什么会因为共同的知乎内容、观点和兴趣而愿意认识另一个人？**

## 二、建议确定的产品主线

建议把产品故事统一成下面这条线：

1. 用户提出一个具体的校园需求，例如组队参赛、找学习搭子、参加活动或寻找同好。
2. 系统结合用户填写的信息，以及知乎兴趣、能力、目标和时间安排进行推荐。
3. 用户看到的不只是一个分数，而是清晰的匹配理由，例如共同关注的话题、回答过的问题、收藏内容或相似目标。
4. 用户点击"表达意向"，等待对方接受。
5. 发布者接受后，两人成为搭子或进入小组，并自动得到破冰话题、首次沟通建议或协作计划。

这条主线同时解决了产品价值、知乎差异化和现场演示问题。演示时可以完整展示"发布需求 → 推荐 → 查看理由 → 表达意向 → 接受 → 成组"的闭环。

## 四、P1：优先提升产品完整度

### 1. 调整匹配逻辑 ✅（已完成）

目前 MBTI 容易成为页面上最显眼的匹配依据，但它不适合承担核心推荐逻辑。建议将 MBTI 降为辅助参考，把真正影响合作成功率的因素放在前面：

- 目标是否一致：参赛、学习、活动、兴趣交流等。
- 时间是否匹配：每周可投入时长、可约时间段、截止日期。
- 合作方式是否匹配：线上/线下、主导/协作、长期/短期。
- 沟通习惯是否匹配：回复频率、会议频率、任务分工偏好。
- 地点是否方便：校区、城市或是否接受纯线上合作。

匹配分建议拆解展示，例如"目标 40% + 时间 25% + 能力 20% + 沟通方式 10% + MBTI 5%"。具体比例可以调整，但用户必须能看懂分数从哪里来。

### 2. 增加竞赛组队问卷模板 ✅（已完成）

问卷不应只问兴趣和性格，要直接服务于组队。建议增加：

- 想参加的比赛或项目类型。
- 擅长的角色：产品、设计、前端、后端、算法、运营、答辩等。
- 当前项目阶段和期望加入阶段。
- 每周能投入多少时间，最晚可合作到什么时候。
- 希望的队伍规模，以及是否接受跨校、线上合作。

> 落地：在「设计筛选问卷」编辑器顶部新增「竞赛组队模板（8 题）」一键套用按钮，预填上述 8 类关键题；发布时间题模板套用后可增删题目，并逐题勾选「期望」以启用问卷匹配计分（未勾选则为中性分）。见 `COMPETITION_QN_TEMPLATE`（`frontend/js/app.js`）与 `data-qn-template-comp`（`frontend/pages/requests.html`）。

### 3. 让讨论区与搭子请求连接起来 🔶（部分完成）

讨论区不应只是一个静态页面。帖子底部可以增加"我也想参加""申请成为搭子"等入口，点击后带上帖子主题和需求信息，直接创建搭子请求。这样讨论内容才会转化为真实组队行为。

同时建议实现频道切换、发帖、搜索和帖子详情。若时间有限，至少保证一个频道切换和一条帖子发起请求的完整演示。

> 落地：已实现「频道切换」（推荐/搭子/课程/竞赛/生活，按 `channel` 过滤）+ 「帖子转搭子请求」（找搭子/组队帖底部「🤝 申请成为搭子」按钮，点击后带上帖子标题、正文、标签、目的，复用 `POST /api/requests` 一键发起并跳转搭子广场）。发帖、搜索、帖子详情暂未做，见 `initForumPage` / `createRequestFromPost`（`frontend/js/app.js`）。

### 4. 补齐演示和状态 🔶（部分完成）

- 增加演示账号切换，现场可快速切换"发布者"和"申请者"。✅（导航栏"演示账号"下拉，u01~u06）
- 补充加载中、接口失败、空数据、重复提交和请求成功状态。✅（推荐卡 / 身份卡 / 请求列表均有加载中与失败态，按钮发送中禁用）
- 所有表单增加前后端校验，避免空标题、无效时间和重复请求。⬜ 未做
- 重新定义"搭子信评分"：明确它是活跃度、履约情况、被接受率，还是暂时的演示指标。⬜ 未做（仍为演示指标）

## 五、P2：正式版本再做

| 方向 | 建议 |
| --- | --- |
| 知乎 OAuth | 接入真实知乎账号授权，获得用户明确授权后再读取可用资料。 |
| 知乎内容 API | 获取用户公开的关注话题、回答、文章或收藏等内容，建立可解释的兴趣标签。 |
| 数据持久化 | 使用 SQLite 或正式数据库保存用户、问卷、匹配、请求、组队和帖子数据。 |
| 社区治理 | 补充内容审核、举报、拉黑、通知和隐私设置。 |
| 真实信誉体系 | 记录接受率、回复率、合作完成情况和他人评价，逐步形成可信的搭子信评分。 |

## 六、建议开发顺序

1. 先完成知乎内容匹配：推荐卡展示共同内容和可解释理由。
2. 再完成双用户闭环：表达意向、接受请求、成组和破冰建议。
3. 随后调整匹配模型：降低 MBTI 权重，增加时间、角色、合作方式等条件。
4. 再完善讨论区、演示账号、校验和各种状态。
5. 最后再接入 OAuth、数据库、审核和真实信誉分。

这个顺序的核心是先让评委看到"知乎内容如何产生更好的匹配"，再补齐工程能力。

## 七、可直接发给开发的执行清单

现在项目的匹配和问卷链路已经有了，下一步重点不是继续增加页面，而是把"知乎特色"和"成组闭环"做实：

- 首页第一屏突出发布需求和推荐搭子。
- 推荐卡展示共同知乎话题、问题、回答或收藏，并返回明确的匹配理由。
- 后端匹配接口增加 `reasons` 和 `shared_zhihu_contents` 字段，前端不要写死推荐理由。
- 修复"发起搭子"按钮，确保请求能写入后端，并能在另一个账号中被接受。
- 准备两个演示账号，现场完整演示发布需求、匹配、表达意向、接受请求、成组。
- 把 MBTI 从核心分数降为辅助因素，增加角色、时间、投入程度、沟通方式和地点等条件。
- 增加竞赛组队问卷模板，让用户填写比赛类型、擅长角色、可投入时间和合作偏好。
- 让讨论区帖子可以直接转成搭子请求，并补充频道切换、发帖和搜索。
- 补齐加载、失败、空数据、重复提交等状态，并完成前后端校验。
- 修正"知网登录"为"知乎 OAuth 登录"，并在尚未接入真实数据的地方标注 Mock。

黑客松版本先做上述 P0 和关键 P1；OAuth、数据库、审核和真实信誉体系放到 P2。
